# SQL schema conventions

> **In plain English.** Every query in this repository is written against three canonical tables: `users`, `orders`, and `track_events`, plus `message_events` for engagement tiers. Your warehouse will not have these exact tables. It will have something that maps onto them. This page defines the canonical shape, the mapping rules, the naming conventions, and the dialect differences between Snowflake, BigQuery, and PostgreSQL so that a query generated by the engine runs the first time.

## 1. The canonical tables

The engine reasons about customer data in four layers: **identity** (who), **state** (what is true now), **behavior** (what happened), and **transaction** (money that changed hands). The three canonical tables cover them:

| Table | Layer | Grain | Required columns |
|---|---|---|---|
| `users` | identity + state | one row per known person | `user_id`, `email`, `created_at`, `country`, `plan`, `lifecycle_stage`, `email_consent_at`, `sms_consent_at` |
| `orders` | transaction | one row per order (or invoice, payment, subscription period) | `order_id`, `user_id`, `order_at`, `status`, `gross_amount`, `discount_amount`, `net_amount`, `currency` |
| `track_events` | behavior | one row per event | `event_id`, `user_id`, `anonymous_id`, `event_name`, `event_at`, `properties` |
| `message_events` | behavior (messaging) | one row per message event from the ESP | `event_id`, `user_id`, `channel`, `event_name`, `event_at`, `message_id`, `campaign`, `machine_open` |

`message_events` is optional: only the engagement tiers (`engine/agents/engagement.py`) read it, and the
daily job skips that step without it. The engine also writes one table of its own,
`lcm_flow_entries` (below).

### `users`

```sql postgres
CREATE TABLE users (
  user_id           VARCHAR      NOT NULL,   -- stable internal id, never the email
  email             VARCHAR,                 -- lowercased, trimmed; null for anonymous-only records
  created_at        TIMESTAMP    NOT NULL,   -- UTC; first known timestamp
  country           VARCHAR,                 -- ISO 3166-1 alpha-2
  plan              VARCHAR,                 -- current plan or tier, null if none
  lifecycle_stage   VARCHAR,                 -- event-driven stage (see section 4)
  email_consent_at  TIMESTAMP,               -- null means no email consent on record
  sms_consent_at    TIMESTAMP,               -- null means no SMS consent on record
  PRIMARY KEY (user_id)
);
```

### `orders`

```sql postgres
CREATE TABLE orders (
  order_id         VARCHAR        NOT NULL,
  user_id          VARCHAR        NOT NULL,
  order_at         TIMESTAMP      NOT NULL,  -- UTC; when money changed hands, not when the cart was created
  status           VARCHAR        NOT NULL,  -- completed | refunded | cancelled | pending
  gross_amount     NUMERIC(18,2)  NOT NULL,
  discount_amount  NUMERIC(18,2)  NOT NULL DEFAULT 0,
  net_amount       NUMERIC(18,2)  NOT NULL,  -- gross minus discount minus refunds; the number RFM and LTV use
  currency         VARCHAR(3)     NOT NULL,  -- ISO 4217; convert to one reporting currency before aggregating
  PRIMARY KEY (order_id)
);
```

### `track_events`

```sql postgres
CREATE TABLE track_events (
  event_id      VARCHAR    NOT NULL,   -- idempotency key (messageId in Segment, insert_id in Amplitude/Mixpanel)
  user_id       VARCHAR,               -- null until identified
  anonymous_id  VARCHAR,               -- device or cookie id
  event_name    VARCHAR    NOT NULL,   -- object_action in snake_case (section 3)
  event_at      TIMESTAMP  NOT NULL,   -- UTC; client timestamp corrected by received_at where the CDP provides it
  properties    JSON,                  -- VARIANT in Snowflake, JSON in BigQuery, JSONB in Postgres
  PRIMARY KEY (event_id)
);
```

### `message_events`

```sql postgres
CREATE TABLE message_events (
  event_id      VARCHAR    NOT NULL,   -- the ESP's event id, for deduplication
  user_id       VARCHAR    NOT NULL,   -- mapped from the ESP's profile id to users.user_id
  channel       VARCHAR    NOT NULL,   -- email | sms | push
  event_name    VARCHAR    NOT NULL,   -- delivered | opened | clicked | bounced | complained | unsubscribed
  event_at      TIMESTAMP  NOT NULL,   -- UTC
  message_id    VARCHAR,               -- the send (campaign message or flow step)
  campaign      VARCHAR,               -- campaign or flow name
  machine_open  BOOLEAN,               -- true when the ESP flagged the open as automated (Apple Mail Privacy Protection)
  PRIMARY KEY (event_id)
);
```

Export `bounced` for hard bounces only; soft bounces are retried by the ESP and say nothing about the
address. The tiers count clicks, never opens: privacy proxies open mail they fetch, so an open is not
a person, and `machine_open` catches only the ones the ESP could identify.

### `lcm_flow_entries` (written by the engine)

```sql postgres
CREATE TABLE IF NOT EXISTS lcm_flow_entries (
  flow            VARCHAR    NOT NULL,   -- the brief's slug
  user_id         VARCHAR    NOT NULL,
  anchor_date     DATE       NOT NULL,   -- the lapse: last core action, or qualification if none since
  holdout_bucket  INTEGER    NOT NULL,   -- first 7 hex digits of md5(user_id || ':' || flow), mod 100
  in_holdout      BOOLEAN    NOT NULL,
  status          VARCHAR    NOT NULL,   -- pending | pushed
  queued_at       TIMESTAMP  NOT NULL,
  pushed_at       TIMESTAMP,
  PRIMARY KEY (flow, user_id, anchor_date)
);
```

The win-back outbox: the daily job's queue step writes due lapses as pending, the job pushes every
pending row to the ESP, and the mark step sets each row it carried to pushed. Every plan writes this
table's DDL for your warehouse to `cohort/job/ledger_<dialect>.sql`; create it once.

## 2. Resolve the transaction object before anything else

`orders` is a role, not a table name. Before any query that touches value, recency, or repeat purchase, name the object that actually records money received and map it to `orders`:

| Business model | Usual source of truth | Common decoy |
|---|---|---|
| Ecommerce | orders | carts, deals |
| Subscription | subscriptions + payments (one row per paid period) | deals, an MRR field |
| Sales-led B2B | closed-won deals | quotes, forecasts |
| Services, agency, professional | invoices or payments | deals |

Deals record a sales process that nobody maintains after the work is won. Invoices are maintained because accounting requires it. In services businesses the gap between the two is routinely one to two orders of magnitude, and every RFM score, LTV curve, and post-purchase trigger inherits the error. Record the resolved object at the top of every query file:

```text
-- transaction object: billing.invoices (paid), mapped to orders
-- customer definition: at least one row on that object; lifecycle_stage is not used
```

A "customer" is a user with at least one completed transaction on the resolved object. Never a lifecycle stage value, unless the stage is set by automation and that automation has been verified.

## 3. Naming

- Tables: plural snake_case (`track_events`). Columns: snake_case.
- Timestamps end in `_at` and are UTC (`order_at`, `event_at`). Dates end in `_date`. Day counts end in `_days`.
- Money columns end in `_amount` and are in the reporting currency after conversion. Never sum mixed currencies.
- Event names are `object_action` in snake_case, past tense for completed actions: `order_completed`, `signed_up`, `onboarding_step_completed`, `feature_used`, `subscription_cancelled`. The allowed set lives in `config/tracking_plan.json`.
- Event property keys are snake_case and typed; the same key means the same thing on every event (`order_id` is always the order id).
- Derived columns carry their derivation in the name: `recency_days`, `r_score`, `rfm_segment`, `cohort_month`, `months_since_first_order`.
- Scores are integers 1 to 5. Segments are lowercase snake_case strings (`champions`, `at_risk`, `hibernating`, `instant_churn`).

## 4. Lifecycle stage is event-driven

Stages are observable conditions, not opinions. The canonical entry conditions, so that a `lifecycle_stage` column means the same thing in every query:

| Stage | Entry condition |
|---|---|
| `subscriber` | consented to receive, no other qualifying action |
| `lead` | identifiable, no qualifying behavior |
| `activated` | reached the aha event within the activation window |
| `customer` | at least one completed transaction on the resolved object |
| `repeat` | at least two |
| `at_risk` | customer whose recency exceeds the expected purchase cycle |
| `lapsed` | customer whose recency is far beyond the expected cycle |

Most platforms do not move a stage backwards without explicit automation. If the reversion path has not been built, treat `lifecycle_stage` as decorative and compute the stage in SQL from `orders` and `track_events` instead.

## 5. Verify before you filter

For every column a query filters or branches on, check all four before writing the `WHERE`:

| Check | Threshold |
|---|---|
| Exists | mandatory |
| Type matches the operator | mandatory |
| Fill rate | at least 60 percent for segmentation; at least 90 percent for automation branching |
| Staleness | look at the distribution of last-updated, not just presence |

The fill-rate query the engine expects you to run first:

```sql postgres
SELECT
  COUNT(*)                                                AS rows_total,
  AVG(CASE WHEN plan IS NOT NULL THEN 1.0 ELSE 0 END)     AS plan_fill_rate,
  AVG(CASE WHEN country IS NOT NULL THEN 1.0 ELSE 0 END)  AS country_fill_rate,
  AVG(CASE WHEN email_consent_at IS NOT NULL THEN 1.0 ELSE 0 END) AS email_consent_fill_rate
FROM users;
```

A field under 60 percent filled is a research finding, not a segmentation input. Say so in the query header and move on.

## 6. Dialect differences the engine must respect

Every generated query declares its dialect on line one (`-- dialect: snowflake`). These are the differences that break queries most often:

| Operation | PostgreSQL | Snowflake | BigQuery |
|---|---|---|---|
| Days between dates | `d2 - d1` (integer) | `DATEDIFF('day', d1, d2)` | `DATE_DIFF(d2, d1, DAY)` |
| Subtract days | `d - 30` or `d - INTERVAL '30 days'` | `DATEADD(day, -30, d)` | `DATE_SUB(d, INTERVAL 30 DAY)` |
| Timestamp to date | `ts::date` | `ts::date` or `TO_DATE(ts)` | `DATE(ts)` |
| Truncate to month | `DATE_TRUNC('month', d)::date` | `DATE_TRUNC('month', d)` | `DATE_TRUNC(d, MONTH)` |
| Month boundaries crossed (see note 1) | `(EXTRACT(YEAR FROM d2) - EXTRACT(YEAR FROM d1)) * 12 + EXTRACT(MONTH FROM d2) - EXTRACT(MONTH FROM d1)` | `DATEDIFF('month', d1, d2)` | `DATE_DIFF(d2, d1, MONTH)` |
| JSON string value | `properties ->> 'key'` | `properties:key::string` | `JSON_VALUE(properties, '$.key')` |
| JSON number value | `(properties ->> 'key')::numeric` | `properties:key::number` | `CAST(JSON_VALUE(properties, '$.key') AS NUMERIC)` |
| Build a JSON object | `json_build_object('k', v)` | `OBJECT_CONSTRUCT('k', v)` | `TO_JSON_STRING(STRUCT(v AS k))` |
| Safe divide, NULL on a zero divisor (see note 2) | `v / NULLIF(d, 0)` | `v / NULLIF(d, 0)` | `SAFE_DIVIDE(v, d)` |
| Quantile buckets | `NTILE(n) OVER (...)` | same | same |
| Previous and next row | `LAG(x) OVER (...)`, `LEAD(x) OVER (...)` | same | same |
| String aggregation | `STRING_AGG(x, ',')` | `LISTAGG(x, ',')` | `STRING_AGG(x, ',')` |
| Current date | `CURRENT_DATE` | `CURRENT_DATE()` | `CURRENT_DATE()` |

Notes on the two rows that look interchangeable and are not:

1. **Months.** Snowflake's `DATEDIFF('month', ...)` and BigQuery's `DATE_DIFF(..., MONTH)` count month
   boundaries crossed: January 31 to February 1 is 1. PostgreSQL's `age()` counts complete months:
   the same pair is 0. The PostgreSQL expression in the table counts boundaries, so all three agree.
   For "complete months elapsed" on every warehouse, compute days between and divide by 30 (the
   engine's LTV queries use 30-day periods for exactly this reason).
2. **Division.** Snowflake's `DIV0(v, d)` and `DIV0NULL(v, d)` return 0 when the divisor is 0, which
   turns "no data" into a real-looking zero rate. Use `v / NULLIF(d, 0)` there, which returns NULL as
   PostgreSQL and BigQuery's `SAFE_DIVIDE` do.

Rules that follow from the table:

1. Put the as-of date and every lookback window in a `params` CTE and `CROSS JOIN` it. Never scatter `CURRENT_DATE` through a query; a query that cannot be re-run for a past date cannot be audited.
2. Cast timestamps to dates once, in the first CTE, and work in dates after that.
3. `NTILE` splits ties arbitrarily: two users with identical values can land in adjacent buckets. Use it on continuous measures (recency in days, revenue) with a deterministic tiebreaker (`ORDER BY recency_days DESC, user_id`). Band discrete measures with heavy ties instead: on the fixtures 126 of 238 customers have exactly one order, so the RFM reference scores frequency with fixed bands (1, 2, 3, 4 to 5, 6 or more orders). See section 7 for low-frequency businesses.
4. Window functions cannot be nested or referenced in the same `SELECT`'s `WHERE`. Score in one CTE, filter in the next.

## 7. RFM for low-frequency businesses

Quintile RFM needs enough transactions per user for frequency to mean something. If the median customer has one order, substitute:

| Standard | Low-frequency analog |
|---|---|
| Recency | days since last invoice or project close |
| Frequency | lifetime engagement count, or projects delivered |
| Monetary | total billed, and trailing-12-month billed |

Add a fourth dimension where the business is episodic: expected next need, derived from the client's own cycle rather than from purchase intervals.

## 8. How the repository tests its SQL

Every SQL block in the repository declares its dialect, in the fence info string (`sql postgres`, `sql snowflake`, `sql bigquery`) or on its first line (`-- dialect: postgresql`). `engine/repo_check.py`, which runs in CI, then:

1. parses every block in its declared dialect with sqlglot, an open-source SQL parser. A parse is a syntax check, not a compile against a live warehouse: a function the warehouse lacks can still parse;
2. executes every PostgreSQL `SELECT` or `WITH` block on DuckDB, over the deterministic fixtures in `examples/brands/ridgeview_saas/data` (built by `examples/brands/ridgeview_saas/data/make_data.py`). DuckDB implements the PostgreSQL features these queries use; it is not PostgreSQL, so a run is strong evidence, not proof. Blocks that read a materialized output carry `-- no-run` and are parsed only;
3. for the RFM and LTV reference queries, transpiles the Snowflake and BigQuery versions to DuckDB and requires them to reproduce the PostgreSQL output's key columns when transpiled to DuckDB: segment and R, F, M scores for every customer (RFM), observed customers and cumulative LTV for every cohort and period (LTV) (`tests/sql/test_sql.py`). Other columns are not compared.

Nothing in CI runs against a live Snowflake, BigQuery or PostgreSQL account. Run `python3 engine/sql/check.py <file> --dialect <dialect>` on any generated query, and `--run` for PostgreSQL against the fixtures, before it goes into a scheduled job.
